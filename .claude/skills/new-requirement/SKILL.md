# New Requirement Intake

Skill นี้ทำงานแบบ interactive ในบทสนทนาหลัก (ไม่ทำงานแบบ background) เพราะต้องถามคำถามชี้แจงกับ user เป็นระยะ ห้ามข้ามขั้นตอนการถาม-ตอบไปมอบหมายให้ subagent ทำแทน

เป้าหมาย: แปลง requirement ดิบที่ user พูดมา ให้กลายเป็นเอกสาร requirement spec ที่มีโครงสร้าง พร้อมอัปเดต backlog และ log ของโปรเจกต์

## ขั้นตอนการทำงาน

### 1. รับ requirement ดิบ

ถ้า user ยังไม่ได้พิมพ์ requirement มาพร้อมกับการเรียก skill นี้ ให้ถามตรงๆ ว่าอยากบันทึก requirement เรื่องอะไร

### 2. สำรวจ requirement ที่มีอยู่แล้ว

ก่อนตัดสินใจอะไร ให้:
- Glob `docs/01-requirements/01-spec/*.md` เพื่อดูรายชื่อเอกสารทั้งหมด
- Read `docs/01-requirements/backlog.md` (ถ้ามี) เพื่อดูภาพรวม
- Grep หาคำสำคัญของ requirement ใหม่ในเอกสาร spec เดิม เพื่อดูว่ามีเอกสารที่พูดเรื่องเดียวกัน/เกี่ยวข้องกันอยู่แล้วหรือไม่

หากพบว่ามีเอกสารเดิมที่เกี่ยวข้องหรือถูกอ้างอิงถึง **ต้องวิเคราะห์ก่อนว่าควรสร้างเอกสารใหม่ หรือควรอัปเดตเอกสารเดิม** อย่าตัดสินใจเองแบบเงียบๆ ถ้าไม่ชัดเจนว่าควรเลือกทางไหน ให้ถาม user ในขั้นตอนถัดไป

### 3. ชี้แจงส่วนที่ไม่แน่ใจ

ถ้ามีส่วนใดของ requirement ที่ยังไม่ชัดเจน (ขอบเขต, เงื่อนไขทางธุรกิจ, ควรสร้างเอกสารใหม่หรืออัปเดตของเดิม, หรืออื่นๆ) ให้ใช้ AskUserQuestion ถามกับ user เสมอ **ทุกคำถามต้องมีตัวเลือกให้พิจารณาอย่างน้อย 3 แนวทาง** (ไม่ใช่แค่ ใช่/ไม่ใช่) พร้อมคำอธิบาย trade-off สั้นๆ ของแต่ละทางเลือก

ตัวอย่างคำถามเมื่อพบเอกสารเดิมที่เกี่ยวข้อง:
- ตัวเลือก 1: สร้างเอกสาร requirement ใหม่แยกต่างหาก (เหมาะถ้าเป็นฟีเจอร์คนละเรื่องที่บังเอิญเกี่ยวข้องกัน)
- ตัวเลือก 2: อัปเดต/ต่อยอดเอกสารเดิม (เหมาะถ้าเป็นรายละเอียดเพิ่มเติมของ requirement เดิม)
- ตัวเลือก 3: ให้ผู้ช่วยแนะนำแนวทางที่เหมาะสมที่สุดพร้อมเหตุผล แล้วรอ user ยืนยัน

ถามให้ครบทุกจุดที่ไม่แน่ใจก่อนไปขั้นตอนถัดไป จะถามหลายรอบก็ได้ถ้าจำเป็น

### 4. สรุปเนื้อหา requirement ฉบับสมบูรณ์

รวบรวมคำตอบทั้งหมดจาก user เขียนสรุปเป็นเนื้อหา requirement ที่มีหัวข้อ, บริบท, ขอบเขต (in/out scope), acceptance criteria — เตรียมให้พร้อมส่งต่อให้ subagent เขียนไฟล์ (ไม่ต้องเขียนไฟล์เอง)

### 5. เตรียมค่าที่ต้องส่งให้ subagent

- `date`: วันที่ปัจจุบันรูปแบบ `YYYYMMDD` (ดูจาก context วันที่ปัจจุบันของบทสนทนา)
- `topic_slug`: สรุปหัวข้อเป็น kebab-case ภาษาอังกฤษสั้นๆ เช่น `online-payment`
- `decision`: `new` หรือ `update:docs/01-requirements/01-spec/{ไฟล์เดิม}.md` ตามที่ตกลงกับ user ในขั้นตอนที่ 2-3
- เนื้อหาสรุปจากขั้นตอนที่ 4
- รายการเอกสารเดิมที่เกี่ยวข้อง (ถ้ามี) สำหรับใส่เป็น reference

### 6. มอบหมายให้ subagent เขียนไฟล์

เรียก agent `requirement-doc-writer` (ผ่าน Agent tool, `subagent_type: requirement-doc-writer`) พร้อมส่งค่าทั้งหมดจากขั้นตอนที่ 5 ไปในคำสั่งแบบครบถ้วน ให้ subagent นี้เป็นคนจัดการ:
- สร้าง/แก้ไขไฟล์ที่ `docs/01-requirements/01-spec/{YYYYMMDD}-{RUNNING_NO}-{topic_slug}.md`
- อัปเดต `docs/01-requirements/backlog.md`
- เขียน log ที่ `docs/05-log/{YYYYMMDD}-log.md`

### 7. รายงานผลให้ user

หลัง subagent ทำงานเสร็จ สรุปให้ user ทราบสั้นๆ ว่า:
- สร้าง/อัปเดตไฟล์ requirement ที่ path ไหน (ใส่ markdown link)
- backlog และ log ถูกอัปเดตแล้ว
- ไฟล์เหล่านี้ยังอยู่แค่ในเครื่อง (untracked/modified ใน git) ยังไม่ได้ push — ถามว่าต้องการ commit + push หรือไม่ (อย่า push เองโดยไม่ถาม)
