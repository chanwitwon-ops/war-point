# Audit Technical Spec

Skill นี้ทำงานแบบ interactive ในบทสนทนาหลัก การตรวจจริงมอบให้ agent `technical-spec-auditor` ซึ่งเป็น **read-only** — การแก้ต้องกลับไปผ่าน skill ของเอกสารนั้น (`sync-architecture`, `sync-api-db`, `sync-detailed-design`, `sync-nfr`)

**ตัวตรวจกับตัวแก้ต้องแยกกัน** ห้ามให้ auditor แก้เอกสารเองแล้วรายงานว่า "ผ่าน"

## ขั้นตอนการทำงาน

### 1. เช็คว่ามีอะไรให้ตรวจ

- List `docs/02-design/02-technical/` — ถ้ายังไม่มีเอกสารเลย ให้บอก user ตรงๆ แล้วแนะนำให้เริ่มที่ `sync-architecture`
- เช็คด้วย ListAgents ว่ามี session อื่นกำลังแก้เอกสารชุดนี้อยู่หรือไม่ ถ้ามี ให้เตือน user ว่าผลตรวจอาจล้าสมัยทันที

### 2. ถามขอบเขตการตรวจ

ใช้ AskUserQuestion **ตัวเลือกอย่างน้อย 3 แนวทาง**:
- ตรวจทั้งชุด (C1–C10) / ตรวจเฉพาะ traceability กับตัวเลขที่ขัดกัน (เร็วกว่า) / ตรวจเฉพาะไฟล์ที่เพิ่งแก้

ถ้า user เพิ่งสั่งตรวจแบบไม่ระบุ ให้เสนอ "ตรวจทั้งชุด" เป็นค่าแนะนำ

### 3. เรียก agent ตรวจ

เรียก `technical-spec-auditor` (`subagent_type: technical-spec-auditor`) พร้อมระบุขอบเขตและรายการเช็คที่ต้องรัน

### 4. สุ่มยืนยันรายงานด้วยตัวเอง

**อย่าเชื่อรายงานของ agent ตามตัวอักษร** ต้องสุ่มยืนยันเองอย่างน้อย 3 ข้อที่ agent บอกว่าผ่าน โดยเน้นข้อที่เป็นตัวเลข:

- นับ endpoint / entity / NFR ใหม่จากไฟล์จริง แล้วเทียบกับตัวเลขในรายงาน
- เปิดไฟล์ที่ agent บอกว่า traceability ครบ แล้วสุ่ม 3 รหัสไปเทียบกับ feature-list จริง
- ถ้า agent รายงานว่าเช็คใดได้ผล 0 รายการแล้วสรุปว่า "ผ่าน" — **ถือว่าเช็คนั้นพัง ไม่ใช่เอกสารสะอาด** ให้รายงาน user แบบนั้น

ถ้าค่าที่วัดเองไม่ตรง ให้ยึดค่าที่วัดเองและบอก user ว่ารายงานคลาดเคลื่อนตรงไหน

### 5. เสนอแนวทางแก้ให้ user ตัดสินใจ

จัดกลุ่มปัญหาตามความรุนแรง แล้วสำหรับปัญหาระดับรุนแรง/ปานกลาง ให้เสนอทางเลือกอย่างน้อย 3 แนวทางพร้อมข้อดี/ข้อเสีย เช่น แก้เอกสารปลายทางให้ตรงต้นทาง / แก้ต้นทางเพราะปลายทางถูกกว่า / เปิด requirement ใหม่ถ้าเป็นกฎที่ยังไม่เคยตกลง

**ห้ามลงมือแก้เองในขั้นนี้** รอ user เลือกก่อน

### 6. ส่งงานต่อให้ writer agent

เมื่อ user เลือกแล้ว ให้เรียก skill ของเอกสารนั้น (`sync-architecture` / `sync-api-db` / `sync-detailed-design` / `sync-nfr`) โดยส่ง `mode: update` และ **ระบุชัดว่าห้ามแตะไฟล์/รหัสอะไรบ้าง** เพื่อไม่ให้การแก้จุดเดียวไปพังส่วนอื่น

### 7. เขียน log และรายงาน

- เขียน log ต่อท้าย `docs/05-log/{YYYYMMDD}-log.md` ว่าตรวจอะไร พบอะไร แก้อะไรไปบ้าง — **ต่อท้ายเท่านั้น**
- รายงาน user เป็นตารางสรุป พร้อมระบุว่าเช็คใดรันไม่ได้และเพราะอะไร
- แจ้งว่ายังไม่ได้ commit/push และถามก่อน — **อย่า push เองโดยไม่ถาม**
