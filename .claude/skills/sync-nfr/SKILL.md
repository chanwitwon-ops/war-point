# Sync Non-Functional Requirement

Skill นี้ทำงานแบบ interactive **2 จังหวะ** ตามที่สไลด์ระบุ: จังหวะแรกเสนอเป็นตารางให้ user รีวิวก่อน จังหวะที่สองจึงเขียนเอกสาร การเขียนไฟล์จริงมอบให้ agent `nfr-writer`

**หัวใจของ skill นี้: ห้ามเดาตัวเลขแทน user** ตัวเลขเป้าหมายทุกตัวต้องผ่านการยืนยัน

## ขั้นตอนการทำงาน

### 1. สำรวจสถานะปัจจุบัน

- Read `docs/01-requirements/01-spec/*-problem-statement.md` — บริบทผู้ใช้จริง (กี่คน อุปกรณ์อะไร เน็ตแบบไหน)
- Read `docs/01-requirements/feature-list.md`
- Read `docs/02-design/02-technical/architecture.md`, `api-spec.md`, `detailed-design.md` ถ้ามี
- Read `docs/03-testing/01-test-plan/test-plan.md` และ `DESIGN.md` — **ถ้ามีเกณฑ์คุณภาพประกาศไว้แล้ว (เช่น contrast ratio) ให้ยกมาอ้าง ไม่ใช่ตั้งใหม่ให้ขัดกัน**

### 2. จังหวะที่ 1 — เสนอเป็นตารางให้รีวิวก่อน (ยังไม่เขียนไฟล์)

แสดงตารางในบทสนทนา:

| ลำดับ | หมวด | ข้อกำหนดที่เสนอ | ตัวเลขเป้าหมายที่เสนอ | เหตุผล / feature ที่ทำให้จำเป็น | ถ้าไม่ทำตอนนี้จะเกิดอะไร |
|---|---|---|---|---|---|

ครอบคลุมหมวด: Performance, Scalability, Availability & Reliability, Security, Usability, Maintainability, Compatibility

กฎการเสนอ:
- ทุกข้อต้องผูกกับ feature หรือ pain point จริงในเอกสาร — ห้ามยกตัวอย่างลอยๆ จากตำรา
- ตัวเลขที่เสนอต้องบอกที่มาว่าคิดจากอะไร (เช่น "ห้องละ 40 คน ทำแบบทดสอบพร้อมกันช่วงคาบเรียน")
- ถ้าข้อไหนมีหลายทางเลือกของเกณฑ์ (เช่น uptime 99% vs 99.9%) ให้เสนอทั้งสองพร้อมต้นทุนที่ต่างกัน
- ปิดท้ายด้วยสรุปภาพรวมว่าข้อไหนควรทำตั้งแต่แรกและข้อไหนเลื่อนได้ พร้อมเหตุผล

จบจังหวะนี้ **ให้หยุดรอ user รีวิว** อย่าเขียนไฟล์

### 3. ยืนยันกับ user

ใช้ AskUserQuestion **ทุกคำถามมีตัวเลือกอย่างน้อย 3 แนวทาง** ประเด็นที่ต้องถาม:

1. **จะเอา NFR ข้อไหนบ้าง** — ทั้งหมด / เฉพาะที่กระทบสถาปัตยกรรม / เฉพาะหมวดที่เลือก
2. **จะวางไว้ที่ไหน** — เอกสารใหม่ `non-functional-requirement.md` / แทรกในเอกสารเดิม / ทำทั้งสอง (แนะนำเอกสารใหม่ + อ้างอิงจาก architecture เพื่อไม่ให้เอกสารเดิมบวม)
3. **ตัวเลขที่ยังไม่แน่ใจ** — ถามทีละข้อพร้อมเสนอค่า 3 ระดับ (ผ่อนปรน / กลาง / เข้ม) พร้อมต้นทุนของแต่ละระดับ

ข้อที่ user ยังไม่ตัดสินใจ ให้ส่งต่อ agent ในฐานะ "รอ user ตัดสินใจ" **ห้ามใส่ตัวเลขสมมติ**

### 4. มอบหมายให้ subagent เขียนไฟล์

เรียก agent `nfr-writer` (`subagent_type: nfr-writer`) พร้อมส่ง `nfr_items` (พร้อมตัวเลขที่ยืนยันแล้วและเหตุผล), `placement`, `mode`, `date`

ถ้า `placement` มี `inline` ต้องระบุชัดว่าให้แทรกที่ไฟล์ไหน หัวข้อไหน และ **ห้ามแตะส่วนอื่นของไฟล์นั้น**

### 5. ตรวจงานที่ subagent ส่งกลับ

**อย่าเชื่อรายงานของ agent ตามตัวอักษร** ต้องเปิดไฟล์ตรวจเองอย่างน้อย 3 ข้อ:

1. **ทุก NFR มีตัวเลขจริง** — grep หาข้อที่เขียนลอยๆ อย่าง "เร็ว", "สูง", "เพียงพอ" โดยไม่มีตัวเลขกำกับ
2. **ไม่มีตัวเลขที่ agent ตั้งเอง** — เทียบรายการในไฟล์กับ `nfr_items` ที่ส่งไป ต้องตรงกันทุกข้อ ข้อที่ user ยังไม่ตัดสินใจต้องอยู่ในหัวข้อ "รอ user ตัดสินใจ" ไม่ใช่ในตารางหลัก
3. **ไม่ขัดกับ `test-plan.md` และ `DESIGN.md`** — สุ่มเทียบ 2 ค่า

### 6. รายงานผลให้ user

สรุป: path ไฟล์ (markdown link), จำนวน NFR แยกตามหมวด, ข้อที่ยังรอตัดสินใจ, จุดที่ขัดกับเอกสารอื่น (ถ้ามี)
แจ้งว่ายังไม่ได้ commit/push และถามก่อน — **อย่า push เองโดยไม่ถาม**
