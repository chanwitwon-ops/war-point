# Audit Prototype

Skill นี้ทำงานแบบ interactive ในบทสนทนาหลัก การ**ตรวจ**มอบให้ agent `prototype-auditor` (read-only) การ**แก้** prototype มอบให้ `prototype-writer` และการแก้เอกสารมอบให้ writer agent ของเอกสารนั้น — ต้องถาม user ก่อนแก้ทุกครั้ง

## ขั้นตอนการทำงาน

### 1. เลือก prototype ที่จะตรวจ

Glob `docs/02-design/01-prototypes/v*/` ดูว่ามีกี่เวอร์ชัน ถ้ามีมากกว่า 1 และ user ไม่ได้ระบุ ให้ถามว่าจะตรวจเวอร์ชันล่าสุด, ทุกเวอร์ชัน, หรือเวอร์ชันที่ระบุ (แนะนำตรวจทุกเวอร์ชันถ้าเพิ่งแก้ `DESIGN.md` เพราะ token ที่เปลี่ยนกระทบทุกเวอร์ชัน)

### 2. มอบหมายให้ subagent ตรวจ

เรียก agent `prototype-auditor` (Agent tool, `subagent_type: prototype-auditor`) ย้ำในคำสั่งว่า:
- **ห้ามแก้ไฟล์** รายงานพร้อมค่าที่วัดได้จริงเท่านั้น
- ข้อที่วัดได้ (contrast, network request, DOM ที่ถูก render, กฎ boundary) **ต้องรันในเบราว์เซอร์จริง** ห้ามสรุปจากการอ่านโค้ด
- ถ้ารันไม่ได้ ให้ระบุว่า "ยังไม่ได้พิสูจน์" ห้ามเดาว่าผ่าน
- ต้องปิด http server ที่เปิดไว้ตรวจทุกตัวเมื่อเสร็จ

### 3. ตรวจทานรายงานของ subagent (อย่าเชื่อทันที)

**สุ่มยืนยันเองอย่างน้อย 3 ข้อ** ที่ agent บอกว่าผ่าน โดยเฉพาะข้อที่เป็นตัวเลข — บทเรียนจากรอบก่อน: agent เคยรายงานว่า `innerHTML` ของส่วนที่ถูกซ่อนเป็น 0 แต่วัดจริงได้ 1660 ตัวอักษร (เป็นแค่ header ไม่ใช่ข้อมูลหวง จึงไม่ใช่บั๊ก แต่รายงานคลาดเคลื่อน) ถ้าเจอความคลาดเคลื่อน ให้ยึดค่าที่วัดเองและบอก user

### 4. แยกให้ชัดว่า "ฝ่ายไหนผิด" ก่อนเสนอแก้

ความไม่สอดคล้องแก้ได้ 2 ทาง ต้องตัดสินให้ถูกว่าใครเป็นตัวถูก:

- **prototype ผิด** → แก้ prototype (เช่น ใช้สีที่ contrast ไม่ผ่าน, ใส่ฟีเจอร์นอกขอบเขต)
- **เอกสารต้นทางผิด/ล้าสมัย** → แก้เอกสาร (เช่น `DESIGN.md` กำหนด token ที่ใช้จริงไม่ได้, test case อ้างราคาที่ไม่ตรงกับ mock ที่ตกลงกันแล้ว)

ใช้ AskUserQuestion เสนอ**อย่างน้อย 3 แนวทาง** พร้อมข้อดี/ข้อเสียและข้อแนะนำ และระบุให้ชัดว่าแต่ละแนวทางกระทบไฟล์ไหนบ้าง

### 5. ส่งงานแก้ต่อ

- แก้ prototype → `prototype-writer` (ต้องถามก่อนว่าจะแก้โฟลเดอร์เดิมหรือสร้างเวอร์ชันใหม่ — flow เปลี่ยนให้สร้างใหม่, แก้รายละเอียด/บั๊กให้แก้ที่เดิม)
- แก้ `DESIGN.md` → แก้ในบทสนทนาหลักได้ แต่ต้อง**ไล่อัปเดตทุก prototype ที่คัดลอก token ไปแล้ว** และเอกสารทดสอบที่อ้าง token นั้น
- แก้เอกสารทดสอบ → `test-writer` (`mode: update`)
- แก้ feature-list / user-journey → `feature-journey-writer` (`mode: update`)

ทุกครั้งต้องระบุชัดว่า**ห้ามแตะไฟล์/เวอร์ชัน/รหัสอะไร**

### 6. ตรวจซ้ำหลังแก้

เรียก `prototype-auditor` อีกรอบเฉพาะข้อที่แก้ ถ้าแก้ `DESIGN.md` ต้องตรวจ**ทุกเวอร์ชัน** ไม่ใช่แค่เวอร์ชันที่แก้

### 7. เขียน log และรายงาน user

เขียน log **ต่อท้าย** `docs/05-log/{YYYYMMDD}-log.md` ระบุค่าที่วัดได้ก่อน/หลังแก้ (เช่น contrast จากเท่าไหร่เป็นเท่าไหร่) เพื่อให้ย้อนดูได้

รายงาน user เป็นตาราง: ข้อที่พบ / ระดับ / ฝ่ายที่ผิด / สถานะ แล้วถามว่าจะ commit หรือไม่ **อย่า push เองโดยไม่ถาม**
