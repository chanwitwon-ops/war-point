# Audit Backlog & Document Pipeline

Skill นี้ทำงานแบบ interactive ในบทสนทนาหลัก การ**ตรวจ**มอบให้ agent `backlog-auditor` (read-only) การ**แก้**ต้องถาม user ก่อนแล้วส่งต่อให้ writer agent ที่รับผิดชอบเอกสารนั้น

หลักการ: **ตัวตรวจกับตัวแก้ต้องแยกกัน** เพื่อไม่ให้ agent ตรวจสอบไปแก้เอกสารเองแบบเงียบๆ แล้วรายงานว่า "ผ่าน"

## ขั้นตอนการทำงาน

### 1. รับขอบเขตการตรวจ

ถ้า user ไม่ได้ระบุ ให้ตรวจทั้งเส้น (`scope: all`) ถ้า user ระบุเจาะจง (เช่น "ตรวจแค่ฝั่ง test") ให้ส่ง scope นั้นไป

### 2. มอบหมายให้ subagent ตรวจ

เรียก agent `backlog-auditor` (Agent tool, `subagent_type: backlog-auditor`) พร้อมระบุ scope และวันที่ปัจจุบัน ย้ำในคำสั่งว่า **ห้ามแก้ไฟล์ ให้รายงานพร้อมหลักฐานตัวเลขเท่านั้น** และข้อที่รันไม่ได้ต้องบอกว่ารันไม่ได้ ห้ามเดาว่าผ่าน

### 3. ตรวจทานรายงานของ subagent (อย่าเชื่อทันที)

รายงานของ agent อาจคลาดเคลื่อน ให้**สุ่มยืนยันเองอย่างน้อย 3 ข้อ**ที่ agent บอกว่าผ่าน โดยเฉพาะข้อที่เป็นตัวเลข (จำนวน AC/TC, dangling reference, wikilink) ถ้าตัวเลขไม่ตรงกับที่ agent รายงาน ให้ยึดค่าที่คุณวัดเองและบอก user ตรงๆ ว่ารายงานคลาดเคลื่อนตรงไหน

### 4. เสนอแนวทางแก้ให้ user เลือก

ถ้าพบปัญหา **ห้ามแก้เองทันที** ให้ใช้ AskUserQuestion เสนอ**อย่างน้อย 3 แนวทาง** พร้อมข้อดี/ข้อเสียและข้อแนะนำ เช่น

- แก้เอกสารปลายทางให้ตรงกับต้นทาง (เหมาะเมื่อ requirement เป็นตัวถูก)
- แก้/เปิด requirement ใหม่ให้ตรงกับสิ่งที่ทำไปแล้ว (เหมาะเมื่อของจริงถูก แต่เอกสารต้นทางล้าสมัย)
- บันทึกเป็น "ช่องว่างที่พบ (Gap)" ไว้ก่อน ยังไม่แก้ (เหมาะเมื่อยังตัดสินใจไม่ได้ หรือรอ business decision)

จัดลำดับให้ user เห็นว่าอันไหน Blocker อันไหนรอได้

### 5. ส่งงานแก้ต่อให้ writer agent ที่ถูกตัว

| เอกสารที่ต้องแก้ | agent ที่รับผิดชอบ |
|---|---|
| `01-spec/*.md`, `backlog.md` | `requirement-doc-writer` (ผ่าน skill `new-requirement` ถ้าเป็น requirement ใหม่) |
| `feature-list.md`, `user-journey.md` | `feature-journey-writer` |
| `acceptance-criteria.md`, `test-plan.md`, `test-cases/*.md` | `test-writer` |
| `02-design/01-prototypes/**` | `prototype-writer` |

ส่งพร้อม `mode: update` และ**ระบุชัดว่าห้ามแตะไฟล์/รหัสอะไร** เพื่อไม่ให้การแก้จุดเดียวไปพังเอกสารที่ตรวจผ่านแล้ว

### 6. ตรวจซ้ำหลังแก้

เรียก `backlog-auditor` อีกรอบเฉพาะข้อที่แก้ เพื่อยืนยันว่าปิดจริงและไม่มีปัญหาใหม่โผล่

### 7. เขียน log และรายงาน user

เขียน log **ต่อท้าย** `docs/05-log/{YYYYMMDD}-log.md` ระบุ: ตรวจอะไร พบอะไร แก้อะไร และอะไรที่ตัดสินใจไม่แก้พร้อมเหตุผล

รายงาน user เป็นตาราง: ข้อที่พบ / ระดับ / สถานะ (แก้แล้ว / ยังเปิด / ตัดสินใจไม่แก้) แล้วถามว่าจะ commit หรือไม่ **อย่า push เองโดยไม่ถาม**
