# ปัญหาตั้งต้นของโปรเจกต์ (Problem Statement)

- **วันที่บันทึก:** 2026-08-21
- **อัปเดตล่าสุด:** 2026-08-21 — ปิด Open Question ทั้ง 3 ข้อ (ตัวชี้วัดความสำเร็จ, ทิศทางโซลูชัน, บทบาทผู้ใช้)
- **สถานะ:** Confirmed
- **อ้างอิง:** ยกเฉพาะ "ตัวปัญหา" มาจากโปรเจกต์ทดลองเดิม `project_warpoint` (อยู่นอก repository นี้ ไม่ได้นำ requirement spec, design, wireframe หรือซอร์สโค้ดเดิมมาด้วยแม้แต่ชิ้นเดียว)

## บริบท / ที่มา

โปรเจกต์นี้เริ่มใหม่จากศูนย์ใน repository นี้ โดยยกมาเฉพาะ **ตัวปัญหา** จากโปรเจกต์ทดลองเดิม `project_warpoint` ไม่ได้นำ requirement spec, design, wireframe หรือซอร์สโค้ดเดิมมาด้วยแม้แต่ชิ้นเดียว — เจตนาคือเดินตามลำดับ workflow เอกสารของโปรเจกต์ตั้งแต่ขั้นแรกจริงๆ

ปัญหาถูกวิเคราะห์ด้วยเทคนิค **5 Whys** ตามแบบฝึกหัดจากคอร์สอบรมภายนอก

บริบทกลุ่มเป้าหมาย: **นักเรียนระดับประถมศึกษา 1 ห้องเรียน ประมาณ 30 คน, 1 เทอม ประมาณ 4 เดือน**

## ความต้องการ (Requirement)

### อาการที่สังเกตได้ (2 อย่าง)

1. ผู้ปกครองไม่ช่วยทบทวนบทเรียนให้เด็กที่บ้าน
2. เด็กไม่ตั้งใจเรียนในห้องเรียน

### การวิเคราะห์ 5 Whys — สายที่ 1: ผู้ปกครองไม่ช่วยทบทวนบทเรียนที่บ้าน

- ทำไมผู้ปกครองไม่ช่วยทบทวน → ไม่มีเวลา และเชื่อว่าการสอนเป็นหน้าที่ของครูทั้งหมด
- ทำไมถึงเชื่อแบบนั้น → เชื่อว่าโรงเรียน/ครูรับผิดชอบชีวิตลูกทั้งหมดอยู่แล้ว
- ทำไมถึงเชื่อแบบนั้น → ผู้ปกครองกลุ่มนี้เองไม่เคยผ่านระบบการศึกษามาก่อน จึงไม่มีประสบการณ์ตรงว่าการทบทวนบทเรียนที่บ้านคืออะไรและสำคัญอย่างไร
- **Root cause สายที่ 1:** เป็นปัจจัยเชิงรุ่น/ประชากรศาสตร์ของตัวผู้ปกครองเอง — อยู่นอกเหนือที่โปรเจกต์นี้จะไปแก้ที่ตัวผู้ปกครองได้ภายในกรอบเวลาที่มี

### การวิเคราะห์ 5 Whys — สายที่ 2: เด็กไม่ตั้งใจเรียนในห้อง

- ทำไมเด็กไม่ตั้งใจเรียน → บทเรียนน่าเบื่อ
- ทำไมบทเรียนน่าเบื่อ → สอนแบบให้จดตามกระดานเป็นหลัก
- ทำไมถึงสอนแบบนั้น → ครูไม่มีเวลาเตรียมสื่อการสอน
- ทำไมครูไม่มีเวลา → ครูถูกดึงไปทำ **ภาระงานที่ไม่ใช่การสอน** ที่สั่งมาจากเบื้องบน เช่น งานต้อนรับคณะดูงาน, ซ้อมแข่งทักษะ, งานเอกสารรายงาน, งานการเงิน/อาหารกลางวัน/สหกรณ์
- **Root cause สายที่ 2:** เป็นโครงสร้างการจัดสรรภาระงานของโรงเรียน — ครูคนเดียวแก้เองไม่ได้

### ข้อสรุปร่วมของทั้งสองสาย

Root cause ทั้งสองสายมี pattern เดียวกันคือ **อยู่นอกเหนือที่ "คนตัวเล็ก" (ผู้ปกครองและครู) จะแก้ได้ด้วยตัวเอง** ข้อสรุปนี้กำหนดข้อจำกัดสำคัญ 2 ข้อให้ระบบที่จะสร้าง:

1. ระบบต้อง **ทำงานได้โดยไม่ต้องรอให้ต้นเหตุถูกแก้** — ห้ามออกแบบโดยตั้งสมมติฐานว่าผู้ปกครองจะเริ่มมาช่วยทบทวน หรือครูจะมีเวลาว่างเพิ่มขึ้น
2. ระบบต้อง **ไม่เพิ่มภาระให้ครูและผู้ปกครอง** — เพราะถ้าเพิ่มภาระ ระบบจะไปชนกับ root cause ที่ตัวเองพยายามแก้

### ลำดับการแก้ (เฟส)

- **เฟสที่ 1 — แก้ที่ root cause สายที่ 1 (แรงจูงใจของเด็ก)** ทำให้เด็กอยากทบทวนบทเรียนด้วยตัวเอง โดยไม่ต้องพึ่งการกำกับจากผู้ปกครอง **เหตุผลที่ทำก่อน:** ระบบเข้าถึงตัวเด็กได้โดยตรง ไม่ต้องรอความร่วมมือจากผู้ใหญ่ จึงทำเสร็จได้เร็วและเห็นผลก่อน อีกทั้งเป็นฐานที่เฟส 2 ต่อยอดได้
- **เฟสที่ 2 — แก้ที่ root cause สายที่ 2 (เวลาเตรียมสื่อการสอนของครู)** ลดเวลาที่ครูต้องใช้ผลิตสื่อการสอน
- ทั้งสองสายถูกบันทึกไว้เป็นปัญหาที่ต้องแก้เหมือนกัน การจัดลำดับนี้เป็นลำดับการลงมือ **ไม่ใช่การตัดสายที่ 2 ทิ้ง**

### ตัวชี้วัดความสำเร็จ

ผู้ใช้ตัดสินใจแล้ว (2026-08-21) ว่าจะวัด **ทั้งด้านพฤติกรรมและด้านคะแนน** ควบคู่กัน ไม่วัดอย่างเดียวด้านใดด้านหนึ่ง:

- **ด้านพฤติกรรม:** สัดส่วนนักเรียนที่เข้ามาทบทวนบทเรียนนอกเวลาเรียนต่อสัปดาห์ และจำนวนแบบทดสอบที่ทำเสร็จ
- **ด้านคะแนน:** คะแนนเฉลี่ยของห้องเทียบก่อนใช้ระบบกับหลังใช้ระบบ
- **เหตุผลที่ต้องวัดทั้งสองด้าน:** ด้านพฤติกรรมตรงกับ root cause สายที่ 1 ที่ว่าเด็กไม่ได้ทบทวนที่บ้าน ส่วนด้านคะแนนเป็นตัวพิสูจน์ว่าการทบทวนนั้นทำให้เรียนรู้ได้จริง ไม่ใช่แค่เข้ามากดเล่น — วัดอย่างเดียวไม่พอทั้งสองด้าน

## ขอบเขต (Scope)

- **อยู่ในขอบเขต:** อาการที่สังเกตได้, การวิเคราะห์ 5 Whys ทั้งสองสาย, root cause ของแต่ละสาย, ข้อสรุปร่วมและข้อจำกัดที่ตามมา, ลำดับเฟสการแก้
- **ไม่อยู่ในขอบเขต:**
  - **ห้ามระบุโซลูชัน ฟีเจอร์ หน้าจอ หรือเทคโนโลยีใดๆ ทั้งสิ้น** ผู้ใช้ยืนยันชัดเจนว่า "เปิดกว้าง ยังไม่ล็อกทิศทางโซลูชัน" — ขั้น requirement นี้ตอบแค่ว่า *ต้องแก้อะไร* ไม่ใช่ *จะแก้ด้วยอะไร* ทิศทางโซลูชันจะไปตัดสินตอนทำ `feature-list.md`
  - ตัวชี้วัดความสำเร็จเชิงตัวเลข — ผู้ใช้เลือก "ยังไม่กำหนด" ในรอบนี้
  - การนำ requirement/design/โค้ดจากโปรเจกต์ทดลองเดิมมาใช้

## Acceptance Criteria

เอกสารนี้เป็น Problem Statement เกณฑ์จึงเป็นเกณฑ์ความครบถ้วนของการวิเคราะห์ปัญหา:

- [ ] ระบุอาการที่สังเกตได้ครบทั้ง 2 อย่าง พร้อมบริบทกลุ่มเป้าหมาย (ประถม ~30 คน/ห้อง, เทอม ~4 เดือน)
- [ ] มีห่วงโซ่ 5 Whys ที่ไล่อ่านได้ครบทั้ง 2 สาย และระบุ root cause ของแต่ละสายอย่างชัดเจน
- [ ] ระบุข้อสรุปร่วมว่า root cause ทั้งสองสายอยู่นอกการควบคุมของครูและผู้ปกครอง
- [ ] ระบุข้อจำกัดของระบบครบ 2 ข้อ (ทำงานได้โดยไม่ต้องรอแก้ต้นเหตุ + ไม่เพิ่มภาระครูและผู้ปกครอง)
- [ ] ระบุลำดับเฟส (สายที่ 1 ก่อน สายที่ 2 ตาม) พร้อมเหตุผลที่เลือกลำดับนี้
- [ ] ไม่มีการระบุโซลูชัน ฟีเจอร์ หรือเทคโนโลยีใดๆ ในเอกสารนี้
- [ ] requirement ฟีเจอร์ทุกฉบับที่ออกหลังจากนี้ต้อง trace กลับมาที่เอกสารนี้ได้
- [ ] มีตัวชี้วัดความสำเร็จที่วัดได้จริงครบทั้งด้านพฤติกรรมและด้านคะแนน
