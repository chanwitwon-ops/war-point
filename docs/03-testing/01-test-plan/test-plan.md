### 1.2 ไม่อยู่ในขอบเขต

- **FE ระดับ Could (7 ตัว):** FE-10 (AI อ่านออกเสียง), FE-11 (AI ช่วยค้นหาคลิป), FE-26 (เปลี่ยนชนิดสัตว์เลี้ยง/รีเซ็ตได้แต้มคืน), FE-37 (พิมพ์เนื้อหาบทเรียนตรงในระบบ), FE-38 (แบบทดสอบไม่ผูกบทเรียน), FE-40 (แจ้งว่าไฟล์อ่านออกเสียงได้ไหม), FE-43 (โหมดฉายผลการต่อสู้ทั้งห้อง) — รอเลื่อนระดับ MoSCoW ผ่าน `sync-feature-journey` ก่อนจึงจะเขียน AC/test case ให้
- **FE ระดับ Won't (2 ตัว):** FE-35 (บัญชี/หน้าจอผู้ปกครอง), FE-36 (หลายห้องเรียน/หลายโรงเรียน) — มีเพียง AC เชิง Negative ยืนยันว่าไม่มีความสามารถนี้ (AC-FE-01-4, AC-FE-56-3) ไม่มี test case เชิงบวกใดๆ ให้
- **การทดสอบประสิทธิภาพ/โหลด (Performance/Load Testing)** — ไม่อยู่ในขอบเขตของรอบนี้ เพราะยังไม่มีระบบจริงให้วัด
- **ความปลอดภัยเชิงลึก (Penetration Testing / Security Audit)** — ไม่อยู่ในขอบเขตของรอบนี้ ด้วยเหตุผลเดียวกัน
- **ตัวชี้วัดเชิงพฤติกรรมของ Problem Statement** ตามที่ [[../../01-requirements/01-spec/20260821-00-problem-statement|spec 00]] ล็อกไว้ — นักเรียนอย่างน้อย 50% ของห้อง (~15 จาก 30 คน) เข้าทบทวนบทเรียนนอกเวลาเรียนอย่างน้อยสัปดาห์ละครั้ง, คะแนนเฉลี่ยของห้องเพิ่มขึ้นอย่างน้อย 5% เทียบก่อนใช้ระบบ, วัด 2 ครั้งคือกลางเทอม (ประมาณสัปดาห์ที่ 7) และปลายเทอม (ประมาณสัปดาห์ที่ 14) — **ตัวชี้วัดเหล่านี้วัดด้วย test case ซอฟต์แวร์ไม่ได้** ต้องวัดด้วยข้อมูลการใช้งานจริงในห้องเรียนหลังปล่อยใช้งาน (post-launch measurement) ไม่ใช่ช่องว่างของแผนทดสอบนี้ — สอดคล้องกับ Coverage Gap G-07 ที่บันทึกไว้แล้วว่ายังไม่มี FE ใดครอบการรายงานความถี่การทบทวนรายสัปดาห์โดยตรง (FE-52 เก็บได้เฉพาะเวลาเข้าใช้งานล่าสุดค่าเดียว)

## 2. Test Strategy

### 2.1 ระดับการทดสอบ

| ระดับ | ทำได้ในรอบนี้หรือไม่ | รายละเอียด |
|---|---|---|
| Prototype walkthrough | **ทำได้ตอนนี้** | เดินตาม Click-through path ของ README ทั้ง v1/v2 เทียบกับ AC และ test case ทีละข้อ |
| Unit testing | ทำไม่ได้รอบนี้ | ยังไม่มีซอร์สโค้ดจริง (function/module) ในโปรเจกต์ |
| Integration testing | ทำไม่ได้รอบนี้ | ยังไม่มี backend/database จริงให้ต่อกัน (prototype เป็น client-side mock ล้วน) |
| System testing | ทำไม่ได้รอบนี้ | รอจนกว่าจะมีระบบจริงที่ผสาน frontend+backend+ฐานข้อมูล |
| UAT (User Acceptance Testing) | ทำไม่ได้รอบนี้ | วางแผนไว้ว่าจะทำกับครู 1 คน + นักเรียนกลุ่มเล็ก เมื่อระบบจริงพร้อม |

**รอบนี้ทดสอบได้จริงเฉพาะบน prototype** เพราะ repository นี้ยังไม่มีซอร์สโค้ดจริง มีเพียงเอกสารและ prototype แบบ single-file HTML ตามที่ระบุใน `CLAUDE.md` — test case ทุกไฟล์ในรอบนี้จึงเขียนโดยอ้างอิงพฤติกรรมของ prototype v1/v2 เป็นหลัก และ AC เป็นเกณฑ์ตัดสิน "ผ่าน/ไม่ผ่าน"

### 2.2 แนวทาง

- **Shift-Left:** เขียน AC และ test case ตั้งแต่ก่อนมีโค้ดจริง (จาก spec → feature-list → prototype) เพื่อให้พบช่องว่างเร็วที่สุด — สะท้อนอยู่แล้วใน Coverage Gap G-01 ถึง G-11 ของ [[acceptance-criteria|acceptance-criteria]]
- **Risk-based ตาม MoSCoW:** ทดสอบ FE ระดับ **Must ทั้ง 26 ตัวก่อนเสมอ** เพราะเป็นเงื่อนไขที่วงจรแรงจูงใจ (ล็อกอิน → ทบทวนบทเรียน → ทำแบบทดสอบ → ได้แต้ม → เลี้ยงสัตว์เลี้ยง) จะพังทันทีถ้าขาด จากนั้นจึงไล่ FE ระดับ Should ทั้ง 42 ตัวตามลำดับความเสี่ยงในหัวข้อ 4
- **การทดสอบสิทธิ์ตามบทบาท:** ต้องยึด **DESIGN.md ข้อ 4.5 — ซ่อน ไม่ใช่ปิดการใช้งาน** วิธีตรวจคือสลับบทบาท (นักเรียน/ครู) แล้วตรวจ DOM จริงว่าองค์ประกอบที่บทบาทนั้นไม่มีสิทธิ์เห็น **ไม่ปรากฏใน DOM เลย** ไม่ใช่แค่ `disabled` — โดยเฉพาะจุดที่ spec 04 ระบุชัดว่าหน้าครูห้ามมีคำว่าแต้ม/ขั้น/ค่าสเตตัสของสัตว์เลี้ยงปรากฏที่ใดเลย
- **การทดสอบ contrast/touch target ต้องวัดตอน UI มีของจริงอยู่บนจอ** รวม modal/sheet ที่ต้องเปิดก่อนวัด (เช่น modal รีเซ็ต PIN, modal ยืนยันเปลี่ยนชนิดสัตว์เลี้ยง) — ห้ามวัดตอนหน้าจอว่างหรือก่อนเปิด modal เพราะจะพลาดองค์ประกอบที่มีปัญหาไป (บทเรียนจาก my-coffee-store ที่ระบุใน `CLAUDE.md`)

### 2.2.1 ความเสี่ยงเฉพาะของเศรษฐกิจแต้ม (เพิ่มใหม่ 2026-08-22)

`20260821-02-pet-points-and-weekly-arena` ล็อกตารางต้นทุนแต้มต่อขั้นแล้ว (ไข่ 1 / ร่างที่ 1 จ่ายเพิ่ม 5 / ร่างที่ 2 จ่ายเพิ่ม 10 / ร่างที่ 3 จ่ายเพิ่ม 15 / ร่างที่ 4 จ่ายเพิ่ม 20 แต้ม สะสมรวม 51 แต้ม ได้แต้มสเตตัสรวม 250 แต้ม) ตัวเลขชุดนี้เป็นจุดที่ทดสอบพลาดง่ายที่สุดในรอบนี้ ต้องระวังเป็นพิเศษ:

- **ความสับสนระหว่าง "จ่ายเพิ่มขั้นต่อขั้น (incremental)" กับ "ต้องมียอดสะสมถึงเกณฑ์"** — spec ยืนยันชัดว่าเป็นแบบ incremental เช่น นักเรียนมีแต้มใช้ได้ 10 แต้มพอดี ต้องซื้อไข่ได้ (เหลือ 9) แล้วขึ้นร่างที่ 1 ได้ต่อทันที (เหลือ 4) **ถ้าระบบตีความผิดเป็น "ต้องมี 6 แต้มสะสม" หรือ "ต้องมี 51 แต้มก่อนถึงจะขึ้นขั้นแรกได้" ถือว่า fail** — ดู AC-FE-24-9 ใน [[acceptance-criteria|acceptance-criteria]] และ test case คู่ขนานใน `test-cases/pet-growth-economy.md`
- **กฎขอบ (boundary) ต้องกดใช้จริงด้วยค่าที่ขอบ ไม่ใช่อ่านโค้ดหรือคาดเดา** — เช่น แต้มที่ใช้ได้ 14 แต้มต้องขึ้นร่างที่ 3 ไม่ได้ (ต้องการ 15) แต่ 15 แต้มพอดีต้องขึ้นได้ทันที ต้องทดสอบทั้งฝั่งค้าง (`<`) และฝั่งพอดี (`>=`) ของทุกขั้น (1, 5, 10, 15, 20) ไม่ใช่ทดสอบแค่ขั้นเดียวแล้วสรุปว่าขั้นอื่นถูกต้องตามไปด้วย
- **ระบบหารแต้มสเตตัส +50 ต่อขั้นเป็นการกระทำของระบบล้วนๆ นักเรียนต้องไม่มีหน้าจอจัดสรรเอง** — ต้องตรวจด้วยการนับ input/ปุ่มจริงใน DOM (ตาม DESIGN.md ข้อ 4.5) ไม่ใช่ดูด้วยตาว่า "ไม่เห็นช่องให้กรอก" เพราะอาจมี input ที่ซ่อนด้วย CSS แต่ยังอยู่ใน DOM
- **prototype v1 ยังไม่ตรงกับตัวเลขที่ล็อกแล้ว** (ใช้ 30 แต้มคงที่ทุกขั้น, ไม่มีขั้นไข่, มี 5 สายพันธุ์แทนที่จะเป็น 3 สาย) — test case ที่อ้างอิงตัวเลขที่ล็อกแล้ว (AC-FE-24-4 ถึง 24-10, AC-FE-75-*, AC-FE-76-*, AC-FE-77-*) จึง**ยังรันบน prototype v1 ไม่ได้ทั้งหมด** ต้องรอ prototype รอบถัดไป — ดู Coverage Gap G-11 ของ [[acceptance-criteria|acceptance-criteria]] และหัวข้อ "สรุปสถานะ prototype" ท้าย `test-cases/pet-growth-economy.md` และ `test-cases/pet-species-and-egg.md`

### 2.3 เครื่องมือ

- **เบราว์เซอร์เปิดไฟล์ `index.html` ตรงๆ** ทั้ง v1 และ v2 — prototype เป็น single-file self-contained ไม่ต้อง build ไม่ต้องรัน dev server ตามที่ `CLAUDE.md` ระบุไว้
- **การวัด contrast/touch target** อ่านค่าจริงจาก DOM ผ่าน DevTools (คำนวณอัตราส่วน contrast ของสีพื้นหลัง/ตัวอักษรที่ใช้งานจริง ไม่ใช่ค่าที่ประกาศไว้ใน DESIGN.md เฉยๆ) และวัดขนาดพื้นที่กด (`getBoundingClientRect()`) ของทุก element ที่กดได้

**หมายเหตุเพิ่มเติมที่พบระหว่างเขียนเอกสารนี้ (นอกเหนือจากที่ระบุไว้ในคำสั่งงาน):** กลไกตัดสินผลการแข่งขันของ v1 และ v2 **ก็ไม่ตรงกันเองด้วย** — v1 ใช้สูตรกำหนดตายตัว `พลัง = ขั้น × 10` แล้วเทียบตรงๆ (`ชนะ = พลังฉัน > พลังคู่แข่ง`) ไม่ใช่การสุ่ม ส่วน v2 ใช้ `Math.random() < 0.5` สุ่มล้วน 50/50 จริง ทั้งสองสูตรให้ผลลัพธ์ที่ไม่สอดคล้องกันถ้านำมาเทียบเป็นระบบเดียว (v1 บอกว่าคู่แข่งขั้นสูงกว่าชนะเสมอ, v2 บอกว่าไม่ว่าขั้นเท่าไหร่ก็มีโอกาสชนะ 50%) — บันทึกเพิ่มเป็นความเสี่ยง **R-03**

### 3.4 ระบบ/กลไกที่ต้อง mock หรือจัดฉาก

- **การล็อกอิน Google ของครู** — prototype จำลองผลลัพธ์ทั้งหมด ไม่มีการเรียก Google OAuth จริง
- **การอ่านออกเสียงของ AI** — เป็นการสลับสถานะปุ่ม + ข้อความแจ้งเตือนเท่านั้น ไม่มีเสียงจริง
- **การค้นคลิปของ AI** — ใช้ชุดคลิปตัวอย่างคงที่ (`aiSuggestionSeed`) ไม่มีการค้นหาจริง
- **การออกข้อสอบของ AI** — เป็นข้อความจำลอง ไม่มีการเรียก AI จริง
- **การเขียนกลับเข้า Google Sheets** — ไม่มีการเรียก Google Sheets API จริง เป็นการจำลองผลลัพธ์สำเร็จ/รายงานแถวที่ถูกข้าม
- **การจับคู่และตัดสินผลการแข่งขัน** — v1 ใช้สูตรค่าสเตตัส=ขั้น×10 เทียบตรง, v2 ใช้การสุ่ม 50/50 (ดูหัวข้อ 3.3) — ทั้งสองเป็นค่าจำลอง ไม่ใช่สูตรตัดสินจริงของระบบ (ยังไม่ล็อกใน spec 02 ตาม Coverage Gap G-03)
- **ระบบหารแต้มสเตตัส +50 ตามสัดส่วนประจำสายพันธุ์ (FE-77)** — ยังไม่มีสูตรสัดส่วนจริงในทั้ง spec และ prototype (จำนวนค่าสเตตัสยังเป็น placeholder 3 ค่า) การทดสอบผลรวม 50 ต่อขั้นทำได้ตามหลักการ แต่การทดสอบสัดส่วนจริงต่อสายทำไม่ได้จนกว่าทีมจะล็อกตัวเลข (ดู Coverage Gap G-03)

## 5. Entry / Exit Criteria

### 5.1 Entry Criteria (เงื่อนไขก่อนเริ่มทดสอบ)

- AC เขียนครบทุก FE ในขอบเขต (Must 26 + Should 42 = 68 FE) — **ครบแล้ว** ใน [[acceptance-criteria|acceptance-criteria]] (167 รหัส AC, 164 ที่ยังใช้งานจริง)
- test case เขียนครบตามรายการใน [[acceptance-criteria|acceptance-criteria]] หัวข้อ "ส่งต่อไป" ก่อนเริ่มรอบทดสอบจริง — **สถานะปัจจุบัน (2026-08-22): เสร็จแล้ว 4 ไฟล์** (`points-ledger`, `pet-growth-economy`, `pet-species-and-egg`, `weekly-arena` — ครอบกลุ่มสัตว์เลี้ยง/แต้ม/การแข่งขันทั้งหมดตามขอบเขตรอบนี้) **ยังไม่ได้สร้าง 4 ไฟล์** (`student-identity-and-roster`, `teacher-lesson-and-quiz`, `teacher-class-overview`, `score-export-gradebook` — นอกขอบเขตของรอบนี้) ดูหัวข้อ 3.5
- prototype v1 และ v2 เปิดได้จริงด้วยเบราว์เซอร์โดยไม่มี error บน console และผ่านการตรวจ self-contained (0 network request ภายนอก) ตามหัวข้อ 2.3
- Test Data ตามหัวข้อ 3.2 พร้อมใช้งานและไม่มีการแก้ไขค่านอกเหนือจากที่ระบุไว้ในหัวข้อนี้

### 5.2 Exit Criteria (เกณฑ์ผ่านก่อนปล่อยขึ้น production)

| เกณฑ์ | ตัวเลขที่ต้องผ่าน |
|---|---|
| test case ระดับ FE Must | ผ่าน **100%** (26 FE ทุกตัวต้องผ่านทุก test case ของตัวเอง) |
| test case ระดับ FE Should | ผ่านไม่น้อยกว่า **90%** ของจำนวน test case ทั้งหมดในระดับ Should |
| บั๊กระดับ Blocker/Critical | ต้องเป็น **0** รายการค้างอยู่ ณ วันปล่อยใช้งาน |
| Contrast ตาม DESIGN.md ข้อ 4.2 | ผ่าน **ทุก element ที่มีข้อความ ทุกหน้าจอ ทุกบทบาท** รวม modal/sheet — วัดได้จริง ≥ 4.5:1 (ข้อความปกติ) หรือ ≥ 3:1 (ข้อความใหญ่/ไม่ใช่ข้อความ) ครบ **100%** ของจุดที่วัด |

| Prototype self-contained | ต้องมี network request เป็น **0 รายการ** ที่ชี้ออกนอกไฟล์ HTML เอง |
| ข้อมูลหวงข้ามบทบาท | ต้องพบ **0 จุด** ที่แต้ม/ขั้น/ค่าสเตตัส/ชื่อจริงของนักเรียนหลุดไปยังหน้าครู หรือข้อมูลของครูหลุดไปยังฝั่งนักเรียน |
| Coverage Gap ระดับสูง | G-01, G-03, G-04, G-11 (ตัวเลขและ prototype ที่กระทบผลทดสอบโดยตรง) ต้องมีแผนปิดหรือได้รับการยืนยันจากทีมก่อนปล่อยใช้งานจริง แม้จะยังไม่ปิดสมบูรณ์ก็ตาม — **ตารางต้นทุนแต้มต่อขั้น (G-01 ส่วนที่ล็อกแล้ว) ไม่ต้องรออีกต่อไป** เพราะล็อกแล้วตั้งแต่ 2026-08-22 |

### 5.3 เกณฑ์หยุดการทดสอบ (Suspension Criteria)

- พบบั๊กระดับ Blocker ที่ทำให้เดินตาม Click-through path หลักของ UJ ใดๆ ไม่จบ (เช่น ล็อกอินไม่ได้, ทำแบบทดสอบแล้วคะแนนไม่คำนวณ) ต้องหยุดทดสอบรอบนั้นทันทีและแจ้งกลับให้แก้ก่อนทดสอบต่อ
- พบว่าค่า mock ระหว่าง v1/v2 ขัดแย้งกันจนทำให้ผลทดสอบตีความไม่ได้ (เช่นกรณี R-02/R-03) ต้องหยุดเฉพาะ test case ที่เกี่ยวข้องกับจุดนั้น และบันทึกไว้ใน [[../02-test-result/index|02-test-result]] แทนการฝืนสรุปผล
- พบว่า test data ในหัวข้อ 3.2 ถูกแก้ไม่ตรงกับค่าจริงใน prototype ต้องหยุดและซิงก์ค่าใหม่ก่อนทดสอบต่อ เพื่อไม่ให้เกิดปัญหาแบบเดียวกับที่ my-coffee-store เคยเจอ (ค่า mock 2 เวอร์ชันไม่ตรงกันทำให้ test case รันไม่ผ่านทั้งที่ตรรกะถูก)

## 6. Schedule / Milestones

> **ไม่มีการกำหนดวันที่จริงในหัวข้อนี้** เพราะผู้ใช้ยังไม่ได้กำหนดกำหนดการ — ใช้ลำดับ "รอบที่" แทน ตามลำดับงานจริงของโปรเจกต์นี้

| รอบ | เนื้อหา | เงื่อนไขเริ่มต้น |
|---|---|---|
| รอบที่ 1 — Prototype walkthrough | เดินตาม Click-through path ของ v1/v2 เทียบกับ AC และ test case ที่มีอยู่จริง (4 ไฟล์ของกลุ่มสัตว์เลี้ยง/แต้ม/การแข่งขัน ณ 2026-08-22 — ดูหัวข้อ 3.5) ทีละ FE ตามลำดับ Must ก่อน Should — **หมายเหตุ:** เคสที่อ้างอิงตัวเลขเศรษฐกิจแต้มที่ล็อกใหม่ (AC-FE-24-4~10, AC-FE-75-*, AC-FE-76-*, AC-FE-77-*, AC-FE-44-1/2) ยังรันบน prototype v1 ไม่ได้ทั้งหมดตาม Coverage Gap G-11 ต้องข้ามไปก่อนจนกว่าจะมี prototype รอบถัดไป | เมื่อ test case ที่อยู่ในขอบเขตเขียนเสร็จและ Entry Criteria ในหัวข้อ 5.1 ครบ |
| รอบที่ 2 — ปิดช่องว่างค่าที่ยังไม่ล็อก | ทีมตัดสินใจตัวเลขที่ค้างอยู่ใน G-01, G-03, G-04, G-10, G-11 และช่องว่างของ feature-list.md (อัตราแปลงคะแนน, จำนวน/สัดส่วนค่าสเตตัส, พลังพิเศษต่อสาย, ราคาของแต่งตัว, เกณฑ์ไม่เข้าใช้งานนาน) แล้วอัปเดต prototype และ test data ในหัวข้อ 3.2 ให้ตรงกัน | เมื่อรอบที่ 1 รายงานผลครบและพบว่าค่าที่ยังไม่ล็อกกระทบการสรุปผลทดสอบจริง |
| รอบที่ 3 — ทดสอบระบบจริงเมื่อมีโค้ด | ทำ unit / integration / system testing ตามหัวข้อ 2.1 เมื่อโปรเจกต์เริ่มมีซอร์สโค้ดจริง (frontend + backend + ฐานข้อมูล) | เมื่อ `CLAUDE.md` มีการอัปเดตคำสั่ง build/lint/test จริง (สัญญาณว่าเริ่มมีโค้ดในโปรเจกต์) |
| รอบที่ 4 — UAT ในห้องเรียน | ทดสอบกับครู 1 คน + นักเรียนกลุ่มเล็กในสภาพแวดล้อมจริง (มือถือที่บ้าน + อุปกรณ์โรงเรียน) | เมื่อรอบที่ 3 ผ่าน Exit Criteria ในหัวข้อ 5.2 ครบแล้ว |
| ขนานตลอดทุกรอบ — Retest รอบที่พบบั๊ก | ทุกครั้งที่พบบั๊กระดับ Blocker/Critical/Major ต้องแก้แล้ว retest เฉพาะจุดที่แก้ก่อนนับว่าปิดเคสนั้น | ทุกครั้งที่มีรายงานบั๊กใหม่ใน [[../02-test-result/index|02-test-result]] |
| สรุปผลปิดรอบ | รวบรวมผลทดสอบทั้งหมดเข้าสู่ [[../02-test-result/index|02-test-result]] และส่งต่อบทเรียนที่ได้ไปยัง `04-retrospectives` | เมื่อ Exit Criteria ของรอบนั้นครบตามหัวข้อ 5.2 |
