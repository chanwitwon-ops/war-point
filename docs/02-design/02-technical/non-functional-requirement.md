## 1. บริบทที่ใช้ตั้งเกณฑ์

**ขอบเขตฟีเจอร์จริงของโปรเจกต์ไม่เปลี่ยน:** 1 ห้องเรียนประมาณ 30 คน ตาม [[../../01-requirements/01-spec/20260821-00-problem-statement|00-problem-statement]] และ `FE-36` (รองรับหลายห้องเรียน/หลายโรงเรียน) ยังคงเป็นระดับ **Won't** ตาม [[../../01-requirements/feature-list|feature-list]] — เอกสารนี้**ไม่เพิ่ม** `classroom_id`/`school_id` หรือแนวคิด multi-tenant ใดๆ เข้าไปในระบบ และไม่กระทบ [[architecture|architecture.md]], [[database-schema|database-schema.md]], [[api-spec|api-spec.md]] ที่ commit ไปแล้วแต่อย่างใด

**สิ่งที่เพิ่มเข้ามาในเอกสารนี้คือ "buffer ด้านความจุ/โหลด" เท่านั้น** — ผู้ใช้ยืนยันให้ตั้งเป้า NFR หมวด Performance และ Scalability โดยเผื่อโหลดขนาด **~120 คน (เทียบเท่า 4 ห้องเรียน)** เพื่อกันไม่ให้ระบบพังทันทีที่ขนาดจริงมากกว่าที่ประเมินไว้เล็กน้อย (เช่น ครูรวมหลายห้องมาทดลองพร้อมกันในเทอมถัดไป หรือประมาณการจำนวนนักเรียนคลาดเคลื่อน) — **นี่คือการเผื่อ "โหลด" ไม่ใช่การเปิด "ฟีเจอร์หลายห้องเรียน"** สองเรื่องนี้แยกกันโดยสิ้นเชิง: ตัวเลข 120 ในเอกสารนี้เป็นแค่จำนวนแถว/จำนวน concurrent request ที่ระบบต้องรับไหวโดยไม่ต้องเปลี่ยนโครงสร้าง schema หรือ endpoint ใดๆ ที่มีอยู่แล้ว ไม่ใช่การเพิ่ม field แยกห้อง/แยกโรงเรียน หรือการจัดกลุ่มข้อมูลข้ามห้องแต่อย่างใด

**อุปกรณ์และเครือข่ายของผู้ใช้จริง (อ้างอิง [[../../01-requirements/01-spec/20260821-01-lesson-and-quiz-system|01-lesson-and-quiz-system]], [[../../01-requirements/01-spec/20260821-03-student-identity-and-roster|03-student-identity-and-roster]], `FE-33`):**

- **นักเรียน:** ใช้มือถือส่วนตัวที่บ้าน (เน็ตมือถือทั่วไป คุณภาพไม่แน่นอน) เพื่อทบทวนบทเรียนและทำแบบทดสอบนอกเวลาเรียน และใช้แท็บเล็ต/คอมพิวเตอร์ของโรงเรียนในคาบเรียน/คาบคอมพิวเตอร์
- **ครู:** ใช้จอใหญ่ (คอมพิวเตอร์/แท็บเล็ตขนาดใหญ่) โดยเฉพาะตอนเปิดหน้าภาพรวมชั้นเรียน (`FE-57`/`FE-58`) ที่มีตารางข้อมูลหนาแน่น
- **ช่วงเวลาที่มีคนใช้พร้อมกันมากที่สุด (peak):** ช่วงคาบเรียน/คาบทำแบบทดสอบที่นักเรียนทั้งห้องกดส่งคำตอบใกล้เวลาหมดเขตพร้อมกัน (ตรงกับ NFR-04) และช่วงเย็น/หัวค่ำที่นักเรียนทยอยกลับมาทบทวนที่บ้านพร้อมกันหลายคน (ตรงกับ NFR-01)

**ข้อจำกัดด้านทีมงาน:** โปรเจกต์นี้เป็นงานเรียน 1 เทอม (~4 เดือน) **ไม่มีทีม ops ประจำ** คอยเฝ้าระบบตลอดเวลา — เกณฑ์ Availability (NFR-06) และแนวทาง Maintainability (NFR-11, NFR-12) ในเอกสารนี้ตั้งขึ้นให้สอดคล้องกับข้อจำกัดนี้โดยตรง ไม่ใช่ตั้งเป้าระดับ production จริงจังที่ต้องมีทีมเฝ้า 24/7

## 3. รายละเอียดแต่ละข้อ

### NFR-01 — เวลาโหลดหน้าบทเรียน/แบบทดสอบ

- **หมวด:** Performance
- **ข้อกำหนด:** หน้ารายการบทเรียนและหน้าแบบทดสอบต้องแสดงผลเสร็จภายใน **2 วินาที** เมื่อเปิดบนเน็ตมือถือทั่วไป
- **ทำไมต้องมี:** นักเรียนทบทวนบทเรียนนอกเวลาเรียนที่บ้านผ่านมือถือเป็นหลัก (`FE-08`, `FE-09`, `FE-20` ตาม [[../../01-requirements/01-spec/20260821-01-lesson-and-quiz-system|01-lesson-and-quiz-system]]) ซึ่งตรงกับ root cause สายที่ 1 ของ [[../../01-requirements/01-spec/20260821-00-problem-statement|00-problem-statement]] — ถ้าหน้าโหลดช้า เด็กจะเลิกทบทวนกลางคันก่อนที่วงจรแรงจูงใจจะเริ่มทำงานเลย
- **วิธีพิสูจน์:** วัดด้วยเครื่องมือ performance profiling (เช่น Lighthouse/DevTools Network throttling) จำลองสภาพเครือข่าย "เน็ตมือถือทั่วไป" (ไม่ใช่ WiFi ออฟฟิศ) วัดเวลานับจากคำขอแรกจนเนื้อหาบทเรียน/แบบทดสอบแสดงครบบนหน้าจอ (ไม่ใช่แค่ HTML shell)
- **ผลถ้าไม่ทำตั้งแต่แรก:** เกิด technical debt แบบ "โครงสร้างข้อมูล/การ query ที่ไม่รองรับความเร็ว" ซึ่งแก้ทีหลังยากกว่าออกแบบไว้ก่อน (ต้อง refactor endpoint + เพิ่ม caching/index ย้อนหลัง) และเสี่ยงทำให้ตัวชี้วัดความสำเร็จหลักของโปรเจกต์ (นักเรียน ≥ 50% ทบทวนนอกเวลาเรียนสัปดาห์ละครั้ง ตาม `00-problem-statement`) พลาดเป้าโดยที่ไม่เกี่ยวกับเนื้อหาบทเรียนเลย
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-01` (Student Web Client), `CMP-05` (Lesson Content Module), `CMP-06` (Quiz and Assessment Module) และ `CMP-15` (File Storage Gateway) ใน DF-01 — ต้องพิจารณาการโหลดแบบ lazy/progressive สำหรับไฟล์แนบขนาดใหญ่ (`FE-09`) ตั้งแต่ตอนเลือกเทคโนโลยี ไม่ใช่แก้ทีหลัง

### NFR-02 — เวลาแสดงคะแนนหลังตรวจปรนัยอัตโนมัติ

- **หมวด:** Performance
- **ข้อกำหนด:** เมื่อนักเรียนกดส่งคำตอบแบบทดสอบปรนัย (`FE-16`) ระบบต้องแสดงคะแนนที่ตรวจแล้วภายใน **1 วินาที**
- **ทำไมต้องมี:** feedback ทันทีหลังทำแบบทดสอบคือหัวใจของวงจรแรงจูงใจ (ทำแบบทดสอบ → ได้แต้ม → เลี้ยงสัตว์เลี้ยง) — ถ้าดีเลย์นาน เด็กจะไม่รู้สึกว่า "ได้แต้ม" ทันที ซึ่งบั่นทอนแรงจูงใจที่กลไกทั้งระบบถูกออกแบบมาเพื่อสร้างขึ้นโดยตรง
- **วิธีพิสูจน์:** วัดเวลานับจากกดปุ่ม "ส่งคำตอบ" ที่ client จนถึงเวลาที่ response คะแนนกลับมาแสดงผล รวมเวลาที่ `CMP-06` ตรวจคำตอบ + `CMP-07` แปลงคะแนนเป็นแต้ม (ตาม DF-01) วัดที่สภาพเครือข่ายมือถือทั่วไปเช่นเดียวกับ NFR-01
- **ผลถ้าไม่ทำตั้งแต่แรก:** เด็กไม่รู้สึกว่าได้แต้มทันที การเชื่อมโยงเชิงเวลาระหว่าง "การกระทำ" กับ "รางวัล" ที่กลไกเกมนี้ตั้งใจสร้างจะอ่อนลง กระทบแรงจูงใจโดยตรงแม้ว่าตรรกะการตรวจคะแนนจะถูกต้อง 100% ก็ตาม
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-06` (Quiz and Assessment Module) และ `CMP-07` (Points Ledger Module) ที่ต้องทำงานแบบ synchronous ในเส้นทางนี้ (ตรงกับที่ `architecture.md` เลือก 3-tier monolith เพื่อให้ transaction เชิงความสอดคล้องสูงทำได้ในขอบเขตธุรกรรมเดียว) — ห้ามออกแบบให้การตรวจคะแนน/แปลงแต้มเป็น background job แบบ asynchronous เพราะจะทำให้ NFR-02 เป็นไปไม่ได้

### NFR-03 — เวลาโหลดหน้าภาพรวมชั้นเรียนของครู (buffer 120 คน)

- **หมวด:** Performance
- **ข้อกำหนด:** หน้าภาพรวมชั้นเรียนของครู (`FE-57`, `FE-58`) ต้องโหลดเสร็จภายใน **3 วินาที** แม้มีข้อมูลนักเรียนมากถึง **120 คน (buffer ตามหัวข้อ 1)**
- **ทำไมต้องมี:** ตารางข้อมูลของหน้านี้หนาแน่น (สถานะทำ/ไม่ทำ × คะแนนรายชุด × สัญลักษณ์เตือน) และครูมีเวลาจำกัดมาก (root cause สายที่ 2 ของ `00-problem-statement`) — ถ้าโหลดช้าจะเพิ่มภาระครูแทนที่จะลดภาระตามเจตนาของ `20260821-04-teacher-class-overview`
- **วิธีพิสูจน์:** สร้างชุดข้อมูลทดสอบ 120 บัญชีนักเรียน × 3 ชุดแบบทดสอบขึ้นไป (เทียบเคียงขนาดจริงของ `MOCK` ใน test-plan.md แต่ขยายจำนวนแถว) แล้ววัดเวลาโหลดจริงด้วยเครื่องมือ performance profiling
- **ผลถ้าไม่ทำตั้งแต่แรก:** ครูรอนานขึ้นทุกครั้งที่เปิดหน้าภาพรวม เพิ่มภาระแทนที่จะลดภาระ ขัดกับข้อจำกัดหลักของโปรเจกต์ (`00-problem-statement` ข้อ "ระบบต้องไม่เพิ่มภาระให้ครู") โดยตรง
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-11` (Teacher Class Overview Module) และการ query `CMP-16` (Relational Database) — ต้องพิจารณา index ที่เหมาะสมและการ query แบบ join ครั้งเดียวแทนการ query แยกต่อแถวตั้งแต่ตอนออกแบบ `database-schema.md`/`api-spec.md` ไม่ใช่แค่ตอน optimize ทีหลัง

### NFR-04 — รองรับการส่งคำตอบแบบทดสอบพร้อมกัน (buffer 120 คำขอ)

- **หมวด:** Scalability
- **ข้อกำหนด:** ระบบต้องรองรับนักเรียนส่งคำตอบแบบทดสอบพร้อมกันสูงสุด **120 คำขอพร้อมกัน** โดยไม่มี request ล้มเหลว
- **ทำไมต้องมี:** เด็กมักกดส่งคำตอบพร้อมกันตอนใกล้หมดเวลาสอบ ซึ่งเป็นช่วงพีคของคาบเรียน — จำนวน 120 คือ buffer 4 เท่าของขนาดจริง (~30 คน) ตามที่ผู้ใช้ยืนยันในหัวข้อ 1
- **วิธีพิสูจน์:** ทำ load test ยิงคำขอส่งคำตอบพร้อมกัน 120 คำขอในเวลาไล่เลี่ยกัน (เช่นภายใน 1-2 วินาที) นับอัตราคำขอที่สำเร็จเทียบกับที่ล้มเหลว/timeout ต้องได้ 100% สำเร็จ
- **ผลถ้าไม่ทำตั้งแต่แรก:** ระบบล่มหรือ timeout ตอนพีคของคาบเรียน ทำให้แต้มไม่เข้าทั้งที่นักเรียนทำแบบทดสอบเสร็จแล้ว เสียความไว้ใจในระบบทั้งชุด (แต้มคือ "ความพยายามสะสมที่ไม่ควรหาย" ตาม `FE-22`)
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-06` (Quiz Module) → `CMP-07` (Points Ledger Module) → `CMP-16` (Relational Database) ตาม DF-01 — ต้องมี database transaction ที่กันการล็อกยาวเกินไปตอนหลายคนหักแต้ม/บันทึกคะแนนพร้อมกัน (`architecture.md` ระบุเรื่อง idempotent request ไว้แล้วในตาราง data flow ของ DF-01) และควรทดสอบว่า connection pool ของ `CMP-16` รองรับ concurrent write ระดับนี้ได้จริงตอนเลือกเทคโนโลยี

### NFR-05 — รองรับจำนวนบัญชีนักเรียนต่อ deployment (buffer 120 บัญชี)

- **หมวด:** Scalability
- **ข้อกำหนด:** ระบบต้องรองรับจำนวนบัญชีนักเรียนอย่างน้อย **120 บัญชีต่อ deployment** (buffer เดียวกับ NFR-04)
- **ทำไมต้องมี:** เผื่อขนาดจริงมากกว่าที่ประเมินไว้ (~30 คน) โดยไม่ต้องปรับโครงสร้างระบบใหม่ — **ย้ำอีกครั้งตามหัวข้อ 1: นี่ไม่ใช่การรองรับหลายห้องเรียน** เป็นเพียงจำนวนแถวข้อมูลนักเรียนในฐานข้อมูลเดียวที่ระบบต้องรองรับได้โดยไม่มีข้อจำกัด hardcode
- **วิธีพิสูจน์:** สร้างข้อมูลทดสอบ 120 บัญชีจริงในระบบ แล้วตรวจว่าทุกหน้าจอที่เกี่ยวข้อง (ล็อกอิน, นำเข้ารายชื่อ `FE-04`/`FE-50`, หน้าภาพรวมครู `FE-57`/`FE-58`, การจับคู่แข่งขัน) ยังทำงานถูกต้องครบถ้วน ไม่มี error จากการจำกัดจำนวนแถวที่ผิดพลาด (เช่น pagination พัง, limit คำขอ query ผิด)
- **ผลถ้าไม่ทำตั้งแต่แรก:** ถ้ามีการ hardcode ค่าจำกัดไว้ที่ 30 (เช่น ขนาด array คงที่, limit ของ query, ขนาด buffer การนำเข้าไฟล์) ระบบอาจพังหรือตัดข้อมูลทิ้งเงียบๆ เมื่อขนาดจริงเกินกว่าที่ประเมินไว้เพียงเล็กน้อย
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-04` (Roster Management Module) และ `CMP-16` (Relational Database) — ยืนยันว่าการเลือก 3-tier monolith (`architecture.md` ข้อ 1) ยังคงเหมาะสมที่ขนาด buffer 120 นี้ (ไม่ต้องเปลี่ยนเป็น microservices) เพราะยังเป็นสเกลที่เล็กมากในภาพรวม ไม่มีผลกระทบต่อการตัดสินใจสถาปัตยกรรมที่ commit ไปแล้ว

### NFR-06 — Uptime ช่วงเวลาเรียน/ทำการบ้าน

- **หมวด:** Availability & Reliability
- **ข้อกำหนด:** ระบบต้องมี uptime **≥ 99%** ในช่วงเวลาเรียน/ทำการบ้าน (เทียบเท่าระบบล่มได้ไม่เกิน ~3.65 วันต่อปี)
- **ทำไมต้องมี:** โปรเจกต์นี้ไม่มีทีม ops ประจำคอยเฝ้าระบบ (งานเรียน 1 เทอม ~4 เดือน) เกณฑ์ 99% เป็นระดับต้นทุนต่ำที่เหมาะสมกับบริบทนี้ ไม่ใช่ระดับ production ที่ต้องมีทีมเฝ้า 24/7
- **วิธีพิสูจน์:** เก็บ log ช่วงเวลาที่ระบบล่ม/ไม่ตอบสนอง (health check เป็นระยะ) แล้วคำนวณสัดส่วนเวลาที่ระบบพร้อมใช้งานเทียบกับเวลาทั้งหมดในช่วงที่นิยามว่าเป็น "เวลาเรียน/ทำการบ้าน" (เช่น 06:00–22:00 ทุกวัน)
- **ผลถ้าไม่ทำตั้งแต่แรก:** ถ้าไม่มีเป้าตัวเลขนี้ตั้งแต่แรก จะไม่มีเกณฑ์ตัดสินว่าระบบล่มบ่อยแค่ไหนถึงถือว่ายอมรับไม่ได้ ทำให้การตัดสินใจเรื่อง infrastructure/monitoring ทำได้ยาก (ไม่รู้ว่าต้องลงทุนแค่ไหน)
- **กระทบสถาปัตยกรรมอย่างไร:** สอดคล้องกับเหตุผลที่ `architecture.md` เลือก 3-tier monolith ก้อนเดียว (ข้อ 1 — "ไม่มีทีม DevOps ดูแลหลาย service") — เกณฑ์ 99% นี้ยืนยันว่าการ deploy เป็นก้อนเดียวแบบเรียบง่าย (ไม่ต้องมี redundancy/failover ซับซ้อน) เพียงพอสำหรับข้อจำกัดของโปรเจกต์นี้แล้ว ไม่จำเป็นต้องเพิ่ม component ใหม่

### NFR-07 — ไม่มีข้อมูลแต้ม/สถานะสัตว์เลี้ยงหายจากความล้มเหลวของระบบ

- **หมวด:** Availability & Reliability
- **ข้อกำหนด:** ห้ามข้อมูลแต้มสะสม/แต้มที่ใช้ได้/สถานะสัตว์เลี้ยงหายจากความล้มเหลวของระบบ — **RPO = 0** สำหรับ transaction ที่ commit แล้ว
- **ทำไมต้องมี:** แต้มคือ "ความพยายามสะสม" ของนักเรียนตาม `FE-22` (ยอดแต้มสะสมรวมที่ไม่ลดลงจากการกระทำใดๆ) — ถ้าข้อมูลหายจากความล้มเหลวของระบบ (ไม่ใช่จากกลไกธุรกิจ) จะขัดกับกฎคุ้มครองความเป็นธรรมที่ระบบยืนยันไว้เองตั้งแต่ระดับ requirement
- **วิธีพิสูจน์:** จำลองความล้มเหลวของระบบหลังจาก transaction commit สำเร็จแล้ว (เช่น kill process ของ API Server หรือตัดการเชื่อมต่อ database กลางทาง) แล้วตรวจว่าข้อมูลที่ commit แล้วก่อนหน้านั้นยังอยู่ครบ 100% หลังระบบกลับมาทำงาน
- **ผลถ้าไม่ทำตั้งแต่แรก:** เด็กเสียแต้มที่สะสมมาเพราะระบบพังโดยไม่ใช่ความผิดของตัวเอง ทำลายความไว้ใจทั้งวงจรแรงจูงใจที่ระบบพยายามสร้าง (ทบทวน → ได้แต้ม → เลี้ยงสัตว์เลี้ยง) เพราะเด็กจะรู้สึกว่าความพยายามของตัวเอง "หายไปเฉยๆ" ได้
- **กระทบสถาปัตยกรรมอย่างไร:** ยืนยันการตัดสินใจของ `architecture.md` ที่ให้ `CMP-07` (Points Ledger Module) เป็น single source of truth ของแต้มและบังคับให้การหักแต้มทุกจุด (`CMP-08`, `CMP-09`) ต้องผ่าน `CMP-07` เท่านั้นเพื่อกัน race condition — NFR-07 เพิ่มเงื่อนไขว่าฐานข้อมูล (`CMP-16`) ต้องมี durability ที่รับประกันว่า transaction ที่ commit แล้วไม่หายแม้ระบบล่มกลางทาง (เช่น write-ahead log/replication ที่ต้องพิจารณาตอนเลือกเทคโนโลยี DB จริง)

### NFR-08 — เก็บ PIN แบบ hashed

- **หมวด:** Security
- **ข้อกำหนด:** PIN ของนักเรียนต้องถูกเก็บแบบ hashed เท่านั้น ห้ามเก็บแบบ plaintext ที่ใดในระบบ (บังคับ ไม่มีตัวเลขเชิงปริมาณ)
- **ทำไมต้องมี:** นักเรียนใช้รหัสประจำตัว + PIN แทนอีเมล/รหัสผ่านในการล็อกอิน (`FE-01` ตาม [[../../01-requirements/01-spec/20260821-03-student-identity-and-roster|03-student-identity-and-roster]]) — PIN คือกลไกยืนยันตัวตนเดียวของกลุ่มผู้ใช้ที่เป็นเด็กประถม
- **วิธีพิสูจน์:** ตรวจ schema ของฐานข้อมูลจริงว่าคอลัมน์ที่เก็บ PIN เป็นค่า hash (ไม่ใช่ข้อความล้วน) และตรวจ log/backup ทั้งหมดว่าไม่มี PIN แบบ plaintext หลุดออกมาที่ใดเลย รวมถึงตรวจ error message ที่ endpoint login ว่าไม่ echo PIN ที่กรอกกลับมา
- **ผลถ้าไม่ทำตั้งแต่แรก:** ถ้าข้อมูลรั่วไหล (DB leak, backup หลุด) PIN ของเด็กประถมทั้งห้องจะถูกเปิดเผยโดยตรง กระทบความปลอดภัยของกลุ่มผู้ใช้ที่เปราะบางที่สุดของระบบ และเปิดช่องให้สวมรอยล็อกอินแทนกันได้ทันที
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-03` (Auth and Session Module) โดยตรง — ต้องเลือก hashing algorithm ที่เหมาะสม (เช่น bcrypt/argon2) ตอนเลือกเทคโนโลยีจริง และต้องแน่ใจว่า flow บังคับเปลี่ยน PIN ครั้งแรก (`FE-47`) และรีเซ็ต PIN โดยครู (`FE-02`) ก็ hash ค่าใหม่ทุกครั้งเช่นกัน ไม่ใช่แค่ตอนสร้างบัญชีครั้งแรก

### NFR-09 — จำกัดอัตราลองล็อกอินต่อ IP

- **หมวด:** Security
- **ข้อกำหนด:** จำกัดอัตราการลองล็อกอินที่ endpoint login ไม่เกิน **10 ครั้ง/นาที/IP**
- **ทำไมต้องมี:** เป็นชั้นป้องกันเพิ่มเติมจาก `FE-48` ที่ล็อกเฉพาะต่อบัญชีเดียว — ถ้าไม่มี rate limit ระดับ IP ผู้ไม่หวังดีสามารถเดา PIN ของนักเรียนหลายบัญชีสลับกันจาก IP เดียวเพื่อเลี่ยงการล็อกต่อบัญชีได้
- **วิธีพิสูจน์:** ยิงคำขอ login ผิดซ้ำจาก IP เดียวกันสลับรหัสประจำตัวหลายบัญชีให้เกิน 10 ครั้งภายใน 1 นาที ตรวจว่าคำขอที่เกินเกณฑ์ถูกปฏิเสธด้วยสถานะที่ชัดเจน (ไม่ใช่ error ทั่วไปที่รั่วรายละเอียดภายใน)
- **ผลถ้าไม่ทำตั้งแต่แรก:** เปิดช่องให้เดา PIN ของเพื่อนร่วมห้องได้ทีละหลายบัญชีพร้อมกันจากจุดเดียว ซึ่งเป็นช่องโหว่ที่ `FE-48` (ล็อกต่อบัญชี) เพียงอย่างเดียวปิดไม่ได้
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-03` (Auth and Session Module) — ต้องมี middleware/mechanism ตรวจจับอัตราคำขอต่อ IP ที่ endpoint login ก่อนเข้าสู่ logic ตรวจ PIN เป็นชั้นแยกจากตัวนับความพยายามผิดต่อบัญชีที่ `architecture.md` ออกแบบไว้ให้ `FE-48` แล้ว (ดู Open Decision ข้อจำนวนครั้ง/ระยะเวลาล็อกใน `architecture.md` ข้อ 8 ซึ่งเป็นตัวเลขคนละชุดกับ NFR-09 นี้)

### NFR-10 — Contrast และพื้นที่กดขั้นต่ำ

- **หมวด:** Usability
- **ข้อกำหนด:** ทุก element ที่มีข้อความ/กดได้ต้องมี contrast ≥ 4.5:1 และพื้นที่กด ≥ 48px — **ค่านี้อ้างอิงโดยตรงจาก [[../../../DESIGN.md|DESIGN.md]] ข้อ 4.2/4.3 ที่วัดจริงแล้วเมื่อ 2026-08-21 ไม่ใช่ตัวเลขใหม่ที่เอกสารนี้ตั้งขึ้นเอง**
- **ทำไมต้องมี:** กลุ่มผู้ใช้เป็นเด็กประถมที่อ่านยังไม่คล่องและมีบางส่วนมองเห็นได้ไม่ดีนัก (ตาม [[../../01-requirements/01-spec/20260821-01-lesson-and-quiz-system|01-lesson-and-quiz-system]]) การอ้างค่าเดียวกับ `DESIGN.md` ในเอกสารนี้ป้องกันไม่ให้มี NFR หมวด Usability สองชุดที่อาจขัดกันเองในอนาคต
- **วิธีพิสูจน์:** วัดด้วยวิธีเดียวกับที่ [[../../03-testing/01-test-plan/test-plan|test-plan.md]] หัวข้อ 2.4 กำหนดไว้แล้ว — วัด contrast จริงจาก DOM (ไม่ใช่ค่าที่ประกาศใน token เฉยๆ) และวัดพื้นที่กดด้วย `getBoundingClientRect()` ทุกหน้าจอ ทุกบทบาท รวม modal/sheet ที่ต้องเปิดก่อนวัด และวัดตอน UI มีข้อมูลจริงอยู่ ไม่ใช่ตอนหน้าจอว่าง (บทเรียนจาก my-coffee-store ที่บันทึกไว้ใน `CLAUDE.md`)
- **ผลถ้าไม่ทำตั้งแต่แรก:** ไม่มีผลเพิ่มเติมจากที่ `DESIGN.md` กำหนดไว้แล้ว (เอกสารเดิมมีอยู่แล้วและยืนยันด้วยการวัดจริง) — เหตุผลที่ยังต้องมีข้อนี้ในเอกสาร NFR คือเพื่อความครบถ้วนของหมวด Usability และเพื่อให้ตารางสรุป NFR ทั้ง 13 ข้อในเอกสารนี้ครบทุกหมวดที่ตกลงกันไว้
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-01`/`CMP-02` (Client) เท่านั้น ไม่กระทบชั้น Logic/Data — เป็นเกณฑ์ระดับ UI component ที่ผูกกับ design token ใน `DESIGN.md` โดยตรง

### NFR-11 — Log ทุกจุด error พร้อม timestamp และ context

- **หมวด:** Maintainability
- **ข้อกำหนด:** ทุกจุดที่เกิด error ในระบบต้องถูก log พร้อม timestamp และ context ที่เพียงพอต่อการสืบสาเหตุ (บังคับ ไม่มีตัวเลขเชิงปริมาณ)
- **ทำไมต้องมี:** โปรเจกต์นี้ไม่มีทีม ops ประจำคอยเฝ้าระบบ (ตามหัวข้อ 1) เมื่อเกิดปัญหาต้อง debug ได้เร็วจากข้อมูล log เพียงอย่างเดียว ไม่มีคนคอยสังเกตการณ์แบบ real-time
- **วิธีพิสูจน์:** จำลอง error ในแต่ละโมดูล (`CMP-03` ถึง `CMP-15`) เช่น การเชื่อมต่อ Google OAuth ล้มเหลว, AI Service timeout, การหักแต้มไม่สำเร็จ — ตรวจว่า log ที่บันทึกมี timestamp และ context (เช่น module ที่เกิด, endpoint, role ของผู้ใช้ที่เกี่ยวข้อง) ครบทุกครั้ง
- **ผลถ้าไม่ทำตั้งแต่แรก:** ปัญหาที่เกิดขึ้นจริงจะสืบไม่ได้ว่าพังตรงไหน โดยเฉพาะจุดที่ `architecture.md` ระบุไว้แล้วว่าเป็นความเสี่ยง (เช่น AI Service ล่ม/ช้าใน DF-01, Google OAuth ล่มใน DF-02) ถ้าไม่มี log ที่มี context ครบ การแก้ปัญหาจะต้องเดาแทนการตรวจสอบข้อเท็จจริง
- **กระทบสถาปัตยกรรมอย่างไร:** เป็น cross-cutting concern ที่กระทบทุก `CMP` ในชั้น Logic (`CMP-03` ถึง `CMP-15`) — ควรมี logging convention ร่วมกันตั้งแต่ตอนเลือกเทคโนโลยี (เช่น structured logging format เดียวกันทุกโมดูล) แทนที่จะปล่อยให้แต่ละโมดูล log ต่างรูปแบบกัน

### NFR-12 — ค่าที่ยังไม่ล็อกต้องเป็น config ปรับได้

- **หมวด:** Maintainability
- **ข้อกำหนด:** ค่าตัวเลขที่ยังไม่ล็อกในเอกสาร requirement/technical spec ปัจจุบัน (เช่น ราคาไอเทม, เกณฑ์ "ไม่เข้าใช้งานนาน", จำนวนครั้ง/ระยะเวลาล็อก PIN) ต้องเก็บเป็น config ที่ปรับได้โดยไม่ต้อง deploy ระบบใหม่ (บังคับ ไม่มีตัวเลขเชิงปริมาณ)
- **ทำไมต้องมี:** เอกสารทั้งชุดของโปรเจกต์มี Gap ที่ยังไม่ล็อกตัวเลขจำนวนมาก ยกตัวอย่างที่บันทึกไว้แล้ว: `G-DB-01`/`G-DB-05`/`G-DB-06`/`G-DB-08` ใน [[database-schema|database-schema.md]], รายการที่คล้ายกันใน [[api-spec|api-spec.md]] (`G-API-*`) และ `Gap G-DD-03` ถึง `G-DD-05` ใน [[detailed-design|detailed-design.md]] — ถ้าตัวเลขเหล่านี้ถูก hardcode ไว้ในโค้ด ทุกครั้งที่ user ยืนยันตัวเลขจริง (เช่น ราคาไอเทมจาก `20260823-06-battle-support-items`) จะต้องแก้โค้ดและ deploy ใหม่
- **วิธีพิสูจน์:** เปลี่ยนค่า config จริง (เช่น ราคาไอเทมป้องกันการโจมตีถึงตาย) ผ่านช่องทาง config ที่ออกแบบไว้ (ไฟล์ config/ตาราง config ใน DB/environment variable) แล้วตรวจว่าระบบใช้ค่าใหม่ทันทีในคำขอถัดไป โดยไม่มีการ build/deploy รอบใหม่
- **ผลถ้าไม่ทำตั้งแต่แรก:** ทุกครั้งที่มีการล็อกตัวเลขใหม่จากรอบ `sync-*` ถัดไป (ซึ่งเกิดขึ้นบ่อยตามที่เห็นได้จาก log ของโปรเจกต์นี้) ต้อง deploy ระบบใหม่ทุกครั้ง เพิ่มความเสี่ยงและต้นทุนเวลาที่ไม่จำเป็นสำหรับโปรเจกต์ที่ไม่มีทีม ops ประจำ
- **กระทบสถาปัตยกรรมอย่างไร:** เป็นข้อพิจารณาที่ควรนำไปคิดต่อในรอบ `sync-api-db`/`sync-detailed-design` ถัดไป — อาจต้องมีตาราง config กลาง (เช่น entity สำหรับเก็บค่าที่ปรับได้) หรือกลไก environment-based config เพิ่มเติมจาก `CMP-16` ปัจจุบัน แต่เอกสารนี้ไม่ได้ออกแบบ entity ใหม่แทน `database-schema.md` — เป็นเพียงข้อกำหนดเชิงคุณภาพที่ต้องนำไปพิจารณาตอนออกแบบละเอียด ไม่ใช่การเพิ่มรหัส `ENT-XX` ใหม่ในเอกสารนี้เอง

### NFR-13 — รองรับ browser มือถือและคอมพิวเตอร์โรงเรียน

- **หมวด:** Compatibility
- **ข้อกำหนด:** ระบบต้องรองรับ browser มือถือ (Chrome/Safari) เวอร์ชันล่าสุดลบ 1 (latest − 1) และคอมพิวเตอร์ของโรงเรียน (บังคับ)
- **ทำไมต้องมี:** ตรงกับ `FE-33` (รองรับการใช้งานทั้งบนมือถือและจอขนาดใหญ่) ซึ่งเป็นระดับ Must — นักเรียนใช้ทั้งมือถือที่บ้านและแท็บเล็ต/คอมพิวเตอร์โรงเรียน ครูใช้จอใหญ่ ถ้าไม่รองรับอุปกรณ์ใดอุปกรณ์หนึ่งวงจรแรงจูงใจจะเข้าไม่ถึงเด็กบางกลุ่มทันที
- **วิธีพิสูจน์:** เปิดระบบจริงบน Chrome เวอร์ชันล่าสุดและเวอร์ชันก่อนหน้า 1 เวอร์ชัน, Safari เวอร์ชันล่าสุดและเวอร์ชันก่อนหน้า 1 เวอร์ชัน ทั้งบนมือถือและคอมพิวเตอร์ของโรงเรียน (browser ที่โรงเรียนติดตั้งไว้จริง) ตรวจว่าฟีเจอร์ทุกตัวในขอบเขต (Must+Should ตาม `feature-list.md`) ใช้งานได้ครบ ไม่มีจุดที่ layout พัง/ปุ่มกดไม่ได้
- **ผลถ้าไม่ทำตั้งแต่แรก:** อุปกรณ์จริงของกลุ่มเป้าหมายอาจใช้ระบบไม่ได้เลย โดยเฉพาะกรณีคอมพิวเตอร์โรงเรียนที่มักมี browser เวอร์ชันเก่ากว่ามือถือส่วนตัวของเด็ก
- **กระทบสถาปัตยกรรมอย่างไร:** เกี่ยวข้องกับ `CMP-01`/`CMP-02` (Client) — ต้องเลือกเทคโนโลยี frontend ที่ไม่พึ่งพา API ของ browser รุ่นใหม่ล่าสุดเท่านั้นตอนเลือก stack จริง สอดคล้องกับ `DESIGN.md` ข้อ 4.6 (mobile-first, รองรับทั้งมือถือและจอใหญ่) ที่มีอยู่แล้ว

## 4. NFR ที่ยังไม่ทำในเฟสนี้

รายการต่อไปนี้เป็นระดับ **Should (เลื่อนได้)** ตามที่ผู้ใช้ยืนยัน — ทั้งหมดไม่ใช่การเลื่อนไปทำ "ทีหลังไม่มีกำหนด" แต่เป็นการยอมรับความเสี่ยงในเฟสนี้ของโปรเจกต์งานเรียน 1 เทอม เพื่อโฟกัสทรัพยากรที่มีจำกัดไปที่ NFR ระดับ Must ก่อน:

- **NFR-03 (เวลาโหลดหน้าภาพรวมครูที่ 120 คน)** — เลื่อนได้เพราะขนาดจริงของห้องเรียน (~30 คน) ทำให้หน้านี้เร็วอยู่แล้วโดยธรรมชาติแม้ยังไม่ optimize เป็นพิเศษ ความเสี่ยงที่รับไว้คือถ้าขนาดจริงขยายถึง buffer 120 คนจริง หน้านี้อาจช้ากว่า 3 วินาทีจนกว่าจะกลับมา optimize
- **NFR-06 (Uptime ≥ 99%)** — เลื่อนได้เพราะการวัด uptime อย่างเป็นระบบต้องมี infrastructure สำหรับ health check/monitoring ที่ยังไม่มีในเฟสนี้ (ไม่มีทีม ops ประจำ) ความเสี่ยงที่รับไว้คือระบบอาจล่มโดยไม่มีใครรู้ทันทีจนกว่าจะมีคนมาแจ้ง
- **NFR-09 (Rate limit login ต่อ IP)** — เลื่อนได้เพราะ `FE-48` (ล็อกต่อบัญชี) เป็นชั้นป้องกันหลักที่ทำงานอยู่แล้วในระดับ Should เดียวกัน ความเสี่ยงที่รับไว้คือยังมีช่องโหว่เดา PIN ข้ามหลายบัญชีจาก IP เดียวจนกว่าจะเพิ่มชั้นป้องกันนี้
- **NFR-11 (Log ทุกจุด error พร้อม context)** — เลื่อนได้เพราะยังไม่มีซอร์สโค้ดจริงในโปรเจกต์ (ตามที่ `CLAUDE.md` ระบุ) ความเสี่ยงที่รับไว้คือถ้าเริ่มพัฒนาโค้ดโดยไม่วาง logging convention ไว้ตั้งแต่ต้น จะต้องไล่เพิ่ม log ย้อนหลังทีหลังซึ่งมักตกหล่นบางจุด
- **NFR-12 (ค่าที่ยังไม่ล็อกต้องเป็น config ปรับได้)** — เลื่อนได้ด้วยเหตุผลเดียวกับ NFR-11 (ยังไม่มีโค้ดจริงให้ทำ config) ความเสี่ยงที่รับไว้คือถ้าไม่วางโครง config ไว้ตั้งแต่ต้น ค่าที่ยังไม่ล็อกจำนวนมาก (ดูรายการ Gap ใน `database-schema.md`/`api-spec.md`/`detailed-design.md`) อาจถูก hardcode ไปก่อนโดยไม่ตั้งใจ แล้วต้อง refactor ทีหลัง
